## Accomplishments

- `02_detect_classify.groovy` now reads its full parameterization (anchor name/channel, markers[] name/channel/compartment, exclude_acronyms, k_robust, ring gap/width) from `pipeline.yml` via a line-based mini-parser (no YAML library in QuPath's bundled Groovy) — the former `EXCLUDE_ACRONYMS`/`K_ROBUST`/`GAP_UM`/`RING_WIDTH_UM` literals are gone from the source entirely

- Per-marker bg-sub classifier JSON round-trip renamed to config-driven filenames (`<marker>_Classifier_bgsub.json`), replacing the two legacy literal filenames
- Retired `classify_markers.groovy` — `git mv` to `_archive/retired-scripts/06.1/` with a supersession note, deploy copies removed from both QuPath project directories

## Decisions Made

- pipeline.yml parsing uses a hand-rolled line-based state machine (indentation-tracked blocks for `anchor:`/`markers:`/`ring:`, single-line regex for `exclude_acronyms:`/`k_robust:`), matching the project's existing no-YAML-lib regex-grab convention while correctly handling the nested `markers[]` list
- Bg-sub classifier JSON filenames are now config-driven (`"${marker.name}_Classifier_bgsub.json"`), which changes the on-disk filenames from the two legacy literal names (`Fos_Classifier_20x_bgsub.json`, `TdT_classifier_bgsub.json`); the old files become orphaned but harmless (only this script reads/writes them, and a fresh run regenerates the new filenames since real detection data is present in both project dirs)
- `emitDouble = markers.size() >= 2` implements D-03 structurally rather than as a data-driven check, so the Double+ code path is provably unreachable on a single-marker config
- Compile-verified every commit against QuPath's real bundled classpath (groovy-4.0.26.jar + gson + qupath-core/qupath-core-processing/qupath-gui-fx + qupath-extension-abba-0.4.0 + imglib2) using `org.codehaus.groovy.tools.FileSystemCompiler`, since no headless QuPath CI exists to run the script end-to-end

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Removed the superseded raw-cutoff Fos/TdT reference print**
- **Found during:** Task 2 (Generalize per-marker measurement + compound classification)
- **Issue:** The original script's lines 94-103/398 read two hardcoded legacy filenames (`Fos_Classifier_20x.json`, `TdT_classifier.json`) purely to print a "superseded reference only, NOT operative" advisory line. Under a variable marker set (D-01), these two literal filenames would not exist for a differently-named marker (e.g. a TdT-only config has no `Fos_Classifier_20x.json`), so this block would throw a `FileNotFoundException` and abort the whole script — directly violating the plan's "NO hardcoded marker names" prohibition and blocking correct execution on any non-Fos/TdT config.
- **Fix:** Removed the block entirely (the `fos`/`tdt` legacy `readSpec` calls and the corresponding print line). The block was documented as informational-only and not operative, so removing it does not change classification behavior.
- **Files modified:** scripts/02_detect_classify.groovy (+ 2 deploy copies)
- **Verification:** grep confirms no remaining references to the two legacy filenames or literal channel strings in code; the script compiles cleanly against the real QuPath classpath.
- **Committed in:** `b51657e` (Task 2 commit)

**2. [Rule 1 - Bug] Generalized the ROLLUP_CLASSES list and SC3 sample-cell filter's class-name literals**
- **Found during:** Task 2
- **Issue:** The plan explicitly instructs NOT to alter the SC4 per-region rollup's underlying leaf-heuristic algorithm (superseded by 06.1-03's CR-01 leaf-summed rollup). However, the rollup's `ROLLUP_CLASSES` list and the SC3 sanity-print's sample filter were hardcoded to `["Negative", "Fos+", "TdT+", "Double+", "Excluded"]` / `["Fos+", "TdT+", "Double+"]` — literal marker names that would silently omit a third declared marker's counts (or misrepresent a single-marker config) without erroring.
- **Fix:** Built both lists from the declared marker set (`markers.collect { "${it.name}+" }` plus fixed `Negative`/`Double+` (if emitDouble)/`Excluded`), without touching the underlying leaf-heuristic counting algorithm itself (per the plan's explicit "do not alter the rollup" instruction). For the current Fos+TdT config this produces byte-identical output to the original hardcoded list.
- **Files modified:** scripts/02_detect_classify.groovy (+ 2 deploy copies)
- **Verification:** Manual review confirms the generated class list for the current 2-marker config matches the original literal list exactly; the rollup counting logic (centroid-in-ROI, per-leaf-annotation loop) is untouched.
- **Committed in:** `b51657e` (Task 2 commit)
